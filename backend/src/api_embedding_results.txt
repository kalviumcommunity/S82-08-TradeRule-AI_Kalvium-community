STORAGE STRUCTURE
-----------------

Each generated embedding is stored together with:

- Original source text
- Source metadata
- Embedding vector

Conceptually:

{
    "text": "...",
    "metadata": {
        "source": "...",
        "chunk_index": 0,
        "section": "...",
        "document_type": "..."
    },
    "embedding": [...]
}


ENVIRONMENT CONFIGURATION
-------------------------

The API key is loaded from the existing environment configuration:

GEMINI_API_KEY

The embedding model is loaded from:

EMBEDDING_MODEL

The API base URL is loaded from:

EMBEDDING_BASE_URL

No API secrets are hardcoded in the embedding script.

The .env file remains excluded from version control.


WHY SOURCE AND METADATA ARE STORED WITH THE VECTOR
---------------------------------------------------

A vector by itself only represents the semantic position of
the chunk. During retrieval, the application also needs the
original text to provide context to the language model.

Metadata identifies where the retrieved chunk came from and
allows the application to provide source information.

Therefore, keeping the vector, source text, and metadata
together makes the record useful for later retrieval.


SAME MODEL FOR DOCUMENTS AND QUERIES
------------------------------------

Document chunks and user queries should use the same embedding
model so they are represented in the same vector space.

If different incompatible embedding models are used, similarity
comparisons may no longer be meaningful.


COST AND LATENCY
----------------

As the corpus grows, more chunks require embedding API calls.
This increases processing time and API cost.

Batching multiple chunks in one request can reduce repeated API
calls.

Previously embedded chunks should also be skipped when possible.
A manifest containing chunk identifiers, model names, and
timestamps can help determine which chunks need to be embedded
again.
