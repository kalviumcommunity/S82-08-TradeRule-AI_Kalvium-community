RETRY / BACKOFF DESIGN
======================================================================

The pipeline uses retry handling for temporary embedding API failures.

Maximum attempts: 3

Exponential backoff waits:
  Attempt 1 failure -> wait 1 second
  Attempt 2 failure -> wait 2 seconds
  Attempt 3 failure -> final failure

The implementation keeps failed batches visible in the run
summary instead of silently discarding them.

No transient API failure occurred during the sample run,
so no actual retry was required.


======================================================================
SCALABILITY / RESUMABILITY
======================================================================

Embeddings are persisted after every successful batch.

Each chunk has a stable ID.

Before embedding, the pipeline checks the persistent embedding
store and creates a pending_chunks list containing only chunks
that do not already have embeddings.

This makes the pipeline safe to restart after a crash or
partial execution.

For a corpus too large for one run, the same approach can be
extended into durable jobs or partitions. Each successful batch
would be persisted immediately, allowing later workers or runs
to continue from the remaining chunk IDs while respecting
provider rate limits.
